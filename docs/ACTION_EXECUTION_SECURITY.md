# Action Execution Security Inventory

Date: 2026-10-17
Scope: Python action modules and adjacent process/network/file-operation surfaces reviewed in this pass.

## Policy

1. **No shell interpolation of untrusted values.** Use argument arrays with `shell=False`; validate inputs against explicit allowlists and bounds. Do not construct command strings from model/user text.
2. **AI-generated code uses explicit human consent.** Do not disable a supported action solely because code was generated by AI. `desktop_control` routes generated Python through `core/execution.py` and asks for UI confirmation before execution. It runs in a separate process with a timeout, but is not an OS sandbox and retains the current user's permissions.
3. **Python file execution requires UI confirmation.** `file_processor` routes `.py` files through the central execution engine, validates the path and file size, applies a timeout, and logs the result. The user must approve the action in the UI.
4. **Process execution must be explicit and narrow.** Use argument arrays with `shell=False`, validate paths/arguments, cap timeouts and captured output, and log results. Package installation and generated project commands require explicit UI approval; after approval, proceed without repeatedly prompting for the same workflow.
5. **Writes, deletion, network, system settings, scheduled tasks, and application launches are side effects.** They need validation, least privilege, logging, and confirmation for destructive/irreversible actions.
6. **Network input is untrusted.** Validate URL schemes/hosts where appropriate, apply timeouts and response-size limits, and never execute downloaded content automatically.
7. **Archive extraction and generated output paths must remain within an authorized destination.** Prevent path traversal, symlink escapes, accidental overwrites, and unbounded disk use.

## Changes made in this branch

- `actions/open_app.py`: removed `shell=True` and the constructed `start {app_name}` shell command. Only exact keys from `_APP_ALIASES` are accepted; unknown names are rejected. Windows URI activation uses the OS API; executable launches use argument arrays.
- `actions/computer_settings.py`: replaced shell-based `xrandr` command substitution with direct `xrandr` calls and parsed output values.
- `actions/dev_agent.py`: project generation no longer launches VS Code as an unlisted side effect; the approval preview covers the effects the action will actually perform.
- `actions/desktop.py`: AI-generated desktop tasks are generated as before, then queued for explicit UI confirmation and executed by a timed child process through `core/execution.py`.
- `actions/file_processor.py`: the `code / run` operation now supports Python files after explicit UI confirmation; code review/explanation remain available without confirmation.
- `actions/file_controller.py`: create/write/delete/move/copy/rename/organize operations now queue through the explicit confirmation UI. The banner omits file contents while a SHA-256 fingerprint still distinguishes different requests; read-only actions remain immediate.
- `actions/game_updater.py`: install/update, recurring schedule creation/removal, and any requested shutdown-after-download now require UI approval. Schedule hours/minutes and platform values are validated before side effects. An already-approved scheduled run uses its non-interactive execution path.
- `actions/dev_agent.py`, `core/execution.py`: generated source is checkpointed in the local app task store, while project files stay unchanged until approval. Approved file changes apply atomically with rollback. Dependency installation populates a project-isolated, content-hashed app cache in a resource-limited network-enabled Docker container; project verification uses a disposable bounded source copy and runtime networking is disabled. The development agent refuses host execution when Docker is unavailable.
- `ui.py`: confirmation details now support a scrollable review of long project manifests, including exact file targets and overwrites, rather than silently truncating the approval text.
- `dashboard/server.py`: Windows firewall setup invokes the generated batch file through an explicit `cmd.exe /d /c` argument array with `shell=False`.
- `core/action_loader.py`, `core/plugin_loader.py`: dispatch rejects non-object tool parameters before invoking handlers.

- `core/path_policy.py`: new shared canonical path policy; resolves symlinks before containment checks, rejects absolute child paths and POSIX/Windows traversal forms, and constrains user file processing to the home and temporary directories.
- `actions/file_controller.py`: routes path checks through the shared policy; nested names reject traversal; rename accepts only a single safe name; move/copy into a destination directory resolves the final child path again.
- `actions/file_processor.py`: input paths and generated sibling outputs are checked against allowed roots. Archive extraction no longer calls `shutil.unpack_archive`; ZIP/TAR extraction pre-validates entries, rejects traversal, links and special files, refuses overwrites, and caps extraction at 10,000 entries / 2 GiB.
- `actions/dev_agent.py`: builds persist a task ID, checklist, phase, and hash-verified generated-file checkpoints in a project-bound local store. `task_list`, `task_status`, `task_control` and `resume` provide task controls; pause/cancel take effect between generation calls. Restarted preparation can resume only after explicit request; restarts after approved side effects become uncertain and block replay pending reconciliation. One UI approval shows exact targets, overwrites, dependencies, architecture, acceptance criteria, stack-selected quality checks and their sources, sandbox behavior, and persistent environment cache path. Python adds syntax compilation; JavaScript/TypeScript project scripts are selected only from recognized `package.json` entries and their exact bodies are shown. Checks run sequentially and stop at the first failure; TypeScript without a declared typecheck/build script is not reported verified. Incomplete plans stop before approval; changed files are detected between preview and execution; failed build verification restores original files. Truncated diffs are rejected rather than presented for approval. Only declared packages are installed, into an app-managed cache isolated by project identity, language and requested dependency list; failed installs are discarded, successful caches are content-hashed and reused. Verification runs on a disposable bounded source copy populated from the cache, excluding VCS metadata, caches, symlinks and secret-named files; test artifacts are removed automatically. Audit/fix first require approval to send the listed bounded source snapshot to Gemini; common credential patterns are screened locally and block sharing (location and type only, values hidden); audit findings must match a real file, line, and source excerpt. Audit tests and fix diffs require separate approvals. Fix mode prepares targeted existing-file edits with same-file line evidence, detects concurrent edits and restores original bytes if verification fails. Per-project history is keyed by the canonical path and stores bounded metadata/outcomes, not source text or raw test output. It stops safely above 500 source files / 25 MiB and 50,000 dependency files / 512 MiB. Dependency names are not yet pinned to reviewed versions. Build failures do not trigger an unreviewed repair or unlisted package install.
- `actions/dev_agent.py`, `core/dev_quality.py`: frontend planning records the intended framework, design system, responsive/accessibility expectations and declared external resources. Audit/fix/build share stack-aware commands. Static UI heuristics inspect available source for centralized CSS tokens, breakpoints, image alt text, clickable `div` patterns, framework manifests and remote URLs; they do not render the app or certify accessibility. `import_media` validates a local raster image or font, records exact source/destination paths and hashes in its approval, rechecks paths and hashes at execution, and atomically copies only after approval. SVG and executable formats are excluded. Artwork generation remains in the separate `visual_studio` action; generated images must be explicitly imported into a project.
- Added `tests/test_path_policy.py` for traversal and symlink escapes, plus regression checks for disabled unisolated project execution and shared file policy use.

## Operation reliability, recovery, and audit

- Operations have stable IDs and lifecycle states: `awaiting_confirmation`, `running`, `completed`, `failed`, `cancelled`, `expired`, and `unknown_after_restart`.
- Repeated deliveries of the same tool-call ID return the recorded state instead of starting the side effect again. A deliberate new tool call can repeat the same payload; failed or uncertain calls are not automatically replayed under their original ID.
- A compact JSONL audit journal is written to `~/.marklv/operation_audit.jsonl`. It records timestamps, category, status, duration, and declared permission labels; it intentionally omits command output and payload contents. The journal is size-capped/rotated and is best-effort if the filesystem is unavailable.
- A process restart converts an in-flight operation to `unknown_after_restart`. The app cannot infer whether an external service accepted a request just before a response was lost, so it will not retry that request automatically.
- Execution timeouts are category-limited (desktop and one-off Python files: 60 seconds; general: 60 seconds; project commands and dependency installation: at most 300 seconds). A timed-out direct child is killed where the OS permits it; this is not a guarantee that descendants have exited.
- Undo entries are retained when the reverse action fails and can be retried. Undo state and closures are currently session-memory only; an app restart cannot reconstruct arbitrary Python closures, so durable cross-restart undo is not claimed.
- Plugin code is inspected for a literal `PLUGIN` manifest before import. Untrusted plugins are not imported or executed. Trust and declared capability grants live in `config/plugin_permissions.json`; see `config/plugin_permissions.example.json`. Declared permissions are policy/audit labels, not OS-enforced capabilities. A trusted plugin still runs with the current user's OS permissions. There is no portable OS sandbox for third-party plugins yet; do not trust plugins whose source you have not reviewed.
